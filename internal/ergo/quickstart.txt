{{BOLD}}ergo quickstart{{RESET}}

{{HEADER}}1. WORKFLOW{{RESET}}

On Windows, install Ergo with WinGet:

  {{CMD}}winget install --id Sandover.Ergo --exact{{RESET}}

If WinGet does not find Ergo yet, download the Windows archive from
https://github.com/sandover/ergo/releases/latest, extract `ergo.exe`, and add
its directory to your user `PATH`. Open a new terminal after changing `PATH`.

Initialize the repository, create a task, and use its returned ID:

  {{CMD}}ergo init{{RESET}}
  {{CMD}}ergo new task "Add password login"{{RESET}}
  {{CMD}}ergo list --ready{{RESET}}
  {{CMD}}ergo claim ABCDEF --agent model@host{{RESET}}
  {{CMD}}ergo done ABCDEF -m "Implemented and verified"{{RESET}}

Run `ergo <command> --help` for command syntax and options.

{{HEADER}}2. BACKLOG MODEL{{RESET}}

Each task has a title, optional body, lifecycle state, dependencies, and
timestamps. The backlog owns that current graph. One journal per backlog
owns every task's work history and results. A task is ready when it is todo and
every dependency is complete.

The lifecycle states are:

  draft      staged planning work; visible but unavailable to agents
  todo       open and unclaimed
  doing      claimed by one agent
  blocked    an identified impediment requires action
  done       objective satisfied
  failed     attempt finished without satisfying the objective
  canceled   objective no longer wanted

A draft is unfinished and never ready. A todo task with unmet dependencies is
waiting, not blocked. A claim exists only while a task is doing. Done and
failed are both finished states: either one satisfies a dependency, but only
done records success. Blocked remains unfinished and does not satisfy
dependencies.

An epic is a root task with children. It has no lifecycle state, claim, message,
or result of its own. It finishes when every child is done, failed, or canceled.
A finished epic is failed when any child failed, canceled when none failed and
any child was canceled, and done otherwise. Epics cannot be nested.

{{HEADER}}3. INITIALIZE AND FIND WORK{{RESET}}

  {{CMD}}ergo init{{RESET}}
  {{CMD}}ergo init path/to/repo{{RESET}}
  {{CMD}}ergo where{{RESET}}
  {{CMD}}ergo info{{RESET}}

By default, Ergo discovers `.ergo` by walking upward from the current directory
or from `--dir <path>`. For `init`, a positional directory takes precedence over
`--dir`; without either or a project mapping, Ergo initializes the current
directory. `where` prints the active backlog directory. `info` reports the
running executable and version, source project, owner, storage and log paths,
and how storage was selected.

Personal backlogs and external storage

  {{CMD}}ergo --user aren init{{RESET}}
  {{CMD}}ergo --user aren list{{RESET}}
  {{CMD}}ergo --data-dir /path/to/backlogs/project-a --user aren init{{RESET}}
  {{CMD}}ergo --data-dir /path/to/backlogs/project-a --user aren list{{RESET}}

`--dir` selects the source project; `--data-dir` selects a project-specific
storage base, not a single JSONL file. Shared backlogs live directly in that
base. `--user <id>` selects `users/<id>` beneath it. Each backlog has its own
backlog, journal, lock, and cache. Selecting a colleague's ID selects their
backlog if you have filesystem access; it does not grant permissions. Tasks
and dependencies do not cross backlogs. `--agent` still identifies the worker
claiming a task, not the backlog owner.

IDs contain 1-64 lowercase ASCII letters, digits, hyphens, or underscores.
Windows reserved names such as `con` and `com1` are rejected on every platform.
Ergo does not infer IDs from Git or operating-system accounts.

Without a configured or explicit storage base, personal backlogs live under
`<user-data-dir>/ergo/projects/<project-key>/users/<id>`. The project key hashes
the canonical source path: different projects and worktrees remain separate.
User data roots are `$XDG_DATA_HOME` or `~/.local/share` on Linux,
`~/Library/Application Support` on macOS, and `%LOCALAPPDATA%` on Windows.
Moving a checkout changes its default key; use a mapping for a stable location.

For external or personal storage, Ergo identifies the project using a mapping,
an existing `.ergo` ancestor, or the Git worktree root, in that order. Without
any of these, supply `--dir <project-root>` (or `init <project-root>`). Result
files and their Git evidence always refer to that source project, never the
external backlog directory. No source-local `.ergo` is required.

Global project mappings

Ergo reads `ergo/config.json` under the platform user configuration directory:
Linux `$XDG_CONFIG_HOME` or `~/.config`, macOS `~/Library/Application Support`,
and Windows `%AppData%`. A missing file means no configuration. Malformed files,
unknown fields, unsupported versions, and duplicate canonical roots are errors.
Help, quickstart, and version remain available with invalid configuration.

Example (replace the paths for your machine):

  {
    "version": 1,
    "default_user": "aren",
    "projects": [
      {
        "root": "/path/to/project-a",
        "ergo_data": "/path/to/backlog-repo/project-a",
        "default_backlog": "personal"
      }
    ]
  }

`root` is required. `ergo_data` is optional. `default_backlog` defaults to
`shared`; `personal` requires `default_user` unless `--user` supplies the ID.
`default_user` alone does not switch projects to personal backlogs.

The most specific ancestor mapping wins. Paths are canonicalized, including
symlinks; matching respects directory boundaries. Relative config paths are
relative to the config file's directory. Relative CLI paths are relative to the
working directory. Shell substitutions and `~` inside JSON are not expanded.
On Windows, JSON backslashes must be escaped, or use forward slashes.

Explicit `--data-dir` overrides the mapped storage base. Explicit `--user`
overrides the configured owner; `--shared` overrides a personal default. These
two owner flags conflict. Without an explicit or mapped base, shared storage
remains `<project>/.ergo`, and personal storage uses the user-data location.
Use a separate base per project unless you intentionally want one backlog.

Repeat the same selection flags on every command, or configure a mapping.
Only `init` creates a missing backlog; other commands fail instead of falling
back to shared work. To migrate, stop writers, copy the selected backlog log
and `journal.jsonl` into the target layout, and run `init` there to establish
runtime files. Verify `info`, `list`, and `show` before removing the original.
Do not copy locks or caches, and do not combine legacy and current backlog logs.

Version control is your choice. External/personal initialization adds local
ignore rules for locks and caches without ignoring the authoritative logs.
Track the backlog and journal in a separate Git repository if desired. Ergo
never commits, fetches, merges, or pushes; use your own scripts or scheduler.
Coordinate copies and Git updates with Ergo writers: filesystem locking does
not protect against external Git commands. Resolve divergent logs deliberately,
then verify them with Ergo. Existing tracked source-local files are not moved,
deleted, or untracked automatically.

  {{CMD}}ergo list{{RESET}}                 active work and failed outcomes
  {{CMD}}ergo list --ready{{RESET}}         tasks available to claim
  {{CMD}}ergo list --all{{RESET}}           include closed work
  {{CMD}}ergo list --epic ABCDEF{{RESET}}   one epic and its children
  {{CMD}}ergo show ABCDEF{{RESET}}          inspect one task or epic

`--ready` and `--all` conflict.

Editor integrations can request the same filtered items without depending on
terminal layout:

  {{CMD}}ergo list --all --json{{RESET}}

This writes one versioned JSON document containing an ordered `items` array.
It is a small task-picker projection, not a complete graph export. Normal
`list` output remains the human-readable view. A waiting todo task includes
`waiting_on` with the unfinished dependency IDs that keep it from being ready.

`show` normally produces a complete task document. For a leaf, that document
combines stored fields with synthesized metadata and relationships. For an epic,
it also describes the epic's children. Use `--body` when only the stored body is
wanted:

  {{CMD}}ergo show ABCDEF --body{{RESET}}

The body projection works for leaves and epics. It writes the literal stored
body without headings, metadata, relationships, or other formatting. It adds
and removes no bytes: an empty body produces no output, a body without a final
newline remains without one, and existing trailing newlines remain intact.

Use a temporary file when reading, editing, and replacing a body. Checking
`show` before invoking `body` prevents a failed read from becoming an empty-body
write:

  {{CMD}}tmp=$(mktemp) || exit{{RESET}}
  {{CMD}}trap 'rm -f "$tmp"' 0{{RESET}}
  {{CMD}}ergo show ABCDEF --body >"$tmp" || exit{{RESET}}
  {{CMD}}${EDITOR:-vi} "$tmp" || exit{{RESET}}
  {{CMD}}ergo body ABCDEF <"$tmp"{{RESET}}

In PowerShell, use file redirection through `Start-Process` for literal body
bytes. Save edits as UTF-8 without a byte-order mark, and keep the file's
existing line endings:

  $ergo = (Get-Command ergo -CommandType Application).Source
  $bodyFile = New-TemporaryFile
  try {
    $process = Start-Process -FilePath $ergo `
        -ArgumentList 'show ABCDEF --body' `
        -RedirectStandardOutput $bodyFile.FullName `
        -NoNewWindow -Wait -PassThru
    if ($process.ExitCode -ne 0) { throw "ergo show failed: $($process.ExitCode)" }

    # Edit $bodyFile in an editor that preserves its encoding and line endings.
    $process = Start-Process -FilePath $ergo `
        -ArgumentList 'body ABCDEF' `
        -RedirectStandardInput $bodyFile.FullName `
        -NoNewWindow -Wait -PassThru
    if ($process.ExitCode -ne 0) { throw "ergo body failed: $($process.ExitCode)" }
  }
  finally {
    Remove-Item $bodyFile.FullName
  }

{{HEADER}}4. CREATE AND ORGANIZE{{RESET}}

Create ordinary todo work, or stage it as draft work while you assemble the
graph:

  {{CMD}}ergo new task "Add login"{{RESET}}
  {{CMD}}ergo new task "Add login" --draft{{RESET}}
  {{CMD}}ergo new task "Session tokens" --epic ABCDEF{{RESET}}
  {{CMD}}ergo new task "Session tokens" --epic ABCDEF --draft{{RESET}}

Piped stdin becomes the literal initial body. No pipe or an empty pipe creates
an empty body.

  {{CMD}}printf '%s\n' 'Implement password login.' | ergo new task "Add login"{{RESET}}

For PowerShell, write UTF-8 without a byte-order mark to a temporary file and
redirect that file to Ergo. This keeps PowerShell's text-pipeline formatting
from changing the body bytes:

  $ergo = (Get-Command ergo -CommandType Application).Source
  function Invoke-ErgoWithBody {
    param([string]$Arguments, [string]$Text)
    $inputFile = New-TemporaryFile
    try {
      [IO.File]::WriteAllText(
          $inputFile.FullName, $Text, [Text.UTF8Encoding]::new($false))
      $process = Start-Process -FilePath $ergo `
          -ArgumentList $Arguments `
          -RedirectStandardInput $inputFile.FullName `
          -NoNewWindow -Wait -PassThru
      if ($process.ExitCode -ne 0) { throw "ergo failed: $($process.ExitCode)" }
    }
    finally {
      Remove-Item $inputFile.FullName
    }
  }

  Invoke-ErgoWithBody 'new task "Add login"' 'Implement password login.'
  Invoke-ErgoWithBody 'body ABCDEF' "Revised body`r`n"
  Invoke-ErgoWithBody 'body ABCDEF --append' "`r`n## New context`r`n"
  Invoke-ErgoWithBody 'body ABCDEF' ''

Successful task creation prints only the task ID. This makes the result safe to
use directly:

  {{CMD}}ergo show "$(ergo new task "Investigate timeout")"{{RESET}}

In PowerShell, capture the native command's one-line output as text:

  $id = (ergo new task "Investigate timeout").Trim()
  if ($LASTEXITCODE -ne 0) { throw "ergo new task failed: $LASTEXITCODE" }
  ergo show $id

Create an epic and its children from a Markdown file. `--draft` stages every
child in the atomic batch; the epic itself has no lifecycle state:

  {{CMD}}ergo new epic "Authentication" --file tasks.md{{RESET}}
  {{CMD}}ergo new epic "Authentication" --file tasks.md --draft{{RESET}}

`tasks.md` contains one or more chunks separated by a line that is exactly
`---`. Each chunk starts with `# Title`; its remaining text is the child body.
File order does not add dependencies.

  # Schema
  Create tables and indexes.
  ---
  # Endpoints
  Add signup and login handlers.

Optional piped stdin becomes free-form context on the epic. Successful epic
creation names the epic and every child so they can be used immediately.

Use focused commands to change existing work:

  {{CMD}}ergo title ABCDEF "Clarify authentication failure"{{RESET}}
  {{CMD}}printf '%s\n' 'New body' | ergo body ABCDEF{{RESET}}
  {{CMD}}printf '\n## New context\n' | ergo body ABCDEF --append{{RESET}}
  {{CMD}}printf '' | ergo body ABCDEF{{RESET}}
  {{CMD}}ergo move ABCDEF GHIJKL{{RESET}}
  {{CMD}}ergo move ABCDEF --root{{RESET}}

`body` requires piped stdin and replaces the entire body by default; an empty
pipe clears it. `--append` instead adds the input bytes literally to the stored
body under the write lock. It adds no separator or newline, so include any
desired boundary in the input. Empty append input is a no-op. Move accepts
leaves only. Its destination must be an epic or a clean,
unclaimed root todo or draft task with no results; the latter becomes an epic
when it receives its first child. A staged graph is safe to configure because
draft children cannot be claimed. Once dependency and placement work is done,
open each leaf explicitly:

  {{CMD}}ergo open CHILD01{{RESET}}
  {{CMD}}ergo open CHILD02{{RESET}}

Opening is intentionally one task at a time. It keeps graph construction
atomic at the command level without adding a second transaction mechanism.

{{HEADER}}5. CLAIM AND RESUME{{RESET}}

Use a stable identity such as `model@host`:

  {{CMD}}ergo claim ABCDEF --agent model@host{{RESET}}   claim a known task
  {{CMD}}ergo claim --agent model@host{{RESET}}          claim the oldest ready task

Automatic claim selects a ready todo task. Draft and blocked work must be opened
first. A specific claim can resume todo, doing, done, failed, or canceled work
under the same ID, even if its dependencies are incomplete. This is how work
retries after failure. Repeating a claim as its owner succeeds; another
identity gets a conflict. A legacy error record can still recover through a
specific claim, but `open` rejects legacy error directly.

{{HEADER}}6. OPEN, FINISH, BLOCK, OR CANCEL{{RESET}}

  {{CMD}}ergo open ABCDEF{{RESET}}       draft, doing, or blocked work to todo
  {{CMD}}ergo done ABCDEF{{RESET}}       objective satisfied
  {{CMD}}ergo fail ABCDEF{{RESET}}       attempt finished unsuccessfully
  {{CMD}}ergo block ABCDEF{{RESET}}      impediment requires action
  {{CMD}}ergo cancel ABCDEF{{RESET}}     objective no longer wanted

Draft accepts only `open` and `cancel` as lifecycle transitions. Done, fail,
and block reject draft until it is opened. Open accepts draft, doing, blocked,
and todo; opening todo is an idempotent no-op and writes no journal entry.
Every lifecycle command clears the claim when it changes state. Done, fail,
block, cancel, and open also record the resulting state; opening an already-todo
task remains a no-op unless it carries a message.
Finished work remains retryable through a specific claim, not open.

Use `-m` for terse outcome or attempt context on the automatic journal entry:

  {{CMD}}ergo block ABCDEF -m "Waiting for an API key"{{RESET}}
  {{CMD}}ergo fail ABCDEF -m "CI proves the required target cannot build"{{RESET}}
  {{CMD}}ergo done ABCDEF -m "Implemented" -m "Verified with task ci"{{RESET}}

Repeated `-m` values form paragraphs in one entry. Successful task creation and
state-changing claim, done, fail, block, cancel, and open calls each append one
automatic entry. Reads, structural changes, and no-ops do not. Lifecycle
commands do not read stdin and never replace the task body.

Ergo 6 removes the `release` command. Migrate `release` to `open`; migrate a
blocked direct claim to `open` followed by `claim`. Historical release journal
entries remain readable, but an older Ergo binary cannot read the first draft
record, so upgrade the CLI used by every agent before staging work.

Record any number of explicit results without changing task state:

  {{CMD}}ergo result ABCDEF "Verified the fix"{{RESET}}
  {{CMD}}ergo result ABCDEF "Captured rollout evidence" --file docs/verification.md{{RESET}}

Result text is nonblank and single-line. A result may refer to one existing
project-relative regular file outside `.ergo`. The file remains in the project;
the journal stores its path, hash, modification time, and Git commit when
available. Results work in every readable leaf state and reject epics.

{{HEADER}}7. DEPENDENCIES{{RESET}}

  {{CMD}}ergo sequence TASK_A TASK_B{{RESET}}
  {{CMD}}ergo sequence TASK_A TASK_B TASK_C{{RESET}}
  {{CMD}}ergo unsequence TASK_A TASK_B{{RESET}}

Sequence means A before B before C: each later task depends on the preceding
task. Unsequence removes those adjacent edges. Existing or absent edges are
no-ops. A failed chain writes no partial edges.

Self-dependencies, cycles, and edges between an epic and its child fail. A
dependency on an epic completes when all its children are done, failed, or
canceled. This lets fan-in work continue after every branch reports an outcome;
the epic still renders as failed when any child failed.
Children also inherit dependencies assigned to their epic.

{{HEADER}}8. TERMINAL PRESENTATION{{RESET}}

Ergo uses color to make interactive output easier to scan. The default
`--color=auto` mode adds color when stdout is a terminal and keeps redirected or
piped output plain. It also keeps output plain when `NO_COLOR` is present in the
environment or `TERM=dumb`.

Choose an explicit mode when the destination alone should decide:

  {{CMD}}ergo --color=always list --ready{{RESET}}   include color when piping to a capable viewer
  {{CMD}}ergo --color=never show ABCDEF{{RESET}}     suppress color in terminal output

`always` and `never` override terminal detection, `NO_COLOR`, and `TERM`.
Color decorates generated presentation only; removing Ergo's ANSI decoration
from a colored task document produces the same text as `--color=never`.
User-authored bodies are never decorated. `show --body` always writes the
literal stored bytes without adding ANSI decoration, even with
`--color=always`.

{{HEADER}}9. MAINTENANCE AND CONCURRENCY{{RESET}}

  {{CMD}}ergo prune{{RESET}}        preview removable closed work
  {{CMD}}ergo prune --yes{{RESET}}  remove it from the current backlog
  {{CMD}}ergo compact{{RESET}}      remove superseded event history

Prune targets done, failed, and canceled leaves, then epics left empty. It also
removes their entries from the shared journal. Compact preserves all explicit
results, keeps only the newest automatic entry needed to explain each surviving
task, and migrates legacy messages and results out of the backlog once.

Every task in the selected backlog shares its `journal.jsonl` (by default,
`.ergo/journal.jsonl`); the readable Journal section in `show` is a filtered
rendering of that JSONL, not another file. Leaf show includes the
retained task journal. Epic show includes only each child's latest result. List
keeps the task tree focused on state and readiness, while `list --json` remains
a journal-free task-picker projection.

Projects may track or ignore `journal.jsonl`. Deleting it loses work evidence
but does not corrupt the backlog; the next journal write recreates it. Older
Ergo versions do not understand the split journal or newly written failed-state
records.

Read commands share the repository lock and may run concurrently while each
returns a coherent snapshot. This includes a prune preview.
Writes use the lock exclusively; confirmed prune is a write. Claim selection
and mutation happen under one exclusive lock, so concurrent agents cannot claim
the same task. Commands retain the bounded wait for an incompatible lock.

With git worktrees, a best practice is to let a supervisor agent manage the
backlog, in the main checkout. The supervisor can claim and assign the tasks,
review the work, and mark tasks done. Subagents in worktrees then don't need
to mutate ergo state. Explicit mappings can also let worktrees share one
backlog directory. Divergent copies require deliberate reconciliation; a clean
text merge does not guarantee compatible task state.
